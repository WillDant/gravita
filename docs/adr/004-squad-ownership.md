# 004 — Squads: one session per task, worktrees, and enforced ownership

Status: accepted (Squads, v0.2.0-beta)

## Decision
Gravita orchestrates a Squad as separate Agent SDK sessions, one per task, each role in its own git worktree and branch. A validated `SquadPlan` assigns disjoint path prefixes to roles. Ownership is enforced in three layers: an in-process PreToolUse hook (friendly denial), the permission callback (real approvals), and a commit gate where Gravita diffs the role branch and rejects out-of-scope files. Gravita makes the commits and merges continuously into an integration branch; shared files (lockfiles, root manifest, CI) belong to Gravita and are regenerated, never merged as text. Agents share context through a per-session MCP server bound to their role.

## Consequences
Parallel agents can't overwrite each other; plans are reviewable before any money is spent; each task has its own budget and retry. More moving parts than a single lead session, which remains available as "crew templates" in plain chats.

## Addendum: as built

**Shape.** One `SquadOrchestrator` (engine application layer) runs every squad. A read-only planner session (`Read`/`Grep`/`Glob`, `dontAsk`, structured output) proposes a `SquadPlan` (see *The brief as a conversation* for how it starts); Gravita checks its shape (zod) and its meaning (`validatePlan`) and sends the problems back to the same session, at most three proposals. After the user approves, `SquadScheduler` starts what core's `nextTasks` allows (one task per role, at most three roles, foundation first), `TaskRunner` runs each attempt as its own Claude Code session in the role's worktree, and the phases move on: foundation (contracts frozen at v1 when it ends) → build → verify (the plan's final checks) → deliver. Everything durable is an event; the orchestrator's memory only holds what is in flight.

**Ownership, three layers.**
1. *Guard hook.* An in-process `PreToolUse` hook (it also fires for subagents' calls; a deny wins in every permission mode) runs a pure policy. `Edit`/`Write`/`MultiEdit`/`NotebookEdit` must target a path inside the role's worktree (relative paths resolve from the agent's cwd, `..` followed, the worktree's real path accepted) and inside the role's `owns`, never a shared file or `.git`. For `Bash`, a small shell parser splits the line into simple commands (on `; & | && ||`, newlines and parentheses, honouring quotes), parses `$(…)`, backticks, `sh -c "…"` and `eval` as commands of their own, and peels off wrappers (env assignments, `sudo`, `env`, `time`, `timeout`, `xargs`…). It denies git that changes state (anything but status/diff/log/show/… and the listing forms of branch/tag/stash/worktree/config; `git restore` and `git checkout -- <paths>` are allowed so a role can undo a change), `git -C` outside the worktree, `cd`/`pushd` that leave it (or that it can't resolve: `cd`, `cd ~`, `$VAR`), `rm -r` reaching outside it or deleting it, and `>`/`>>` writing outside it. Reasons are actionable ("backend owns apps/api/ — ask backend with request_change") and name the subagent when one asked. *Limits:* it is a guard, not a shell — interpreters (`node -e`, `python -c`), scripts, symlinks and programs that write files themselves are not seen. That is what the commit gate is for.
2. *Permission policy*, by the autonomy the user picked: `auto` allows everything the guard let through except `AskUserQuestion`; `guarded` allows edits, reads and local commands and sends network/installs (curl, wget, `npm|pnpm|yarn|bun add/install`, `npx`, pip, `git fetch/pull/push`…) and `WebFetch`/`WebSearch` to Needs you; `ask` sends everything but reading. Gravita's own role tools are always allowed.
3. *Commit gate* (the layer that counts). `complete_task` diffs the role's branch against integration: shared files are put back, anything else outside the role's paths stops the commit with `ownership.violation` and goes back to the agent with the paths and how to undo them. The plan's `task` checks run on the commit; a red one goes back the same way. Two returns per run; the third fails the task. Gravita commits; merges into integration run one at a time per squad, and a red `integration` check undoes the merge and sends the task back with the output.

**Role tools.** Each role session gets an in-process MCP server `gravita` bound by closure to its squad, role, task and attempt (no tool takes a role or task id): `whoami`, `get_brief`, `get_task`, `list_tasks`, `report_progress`, `complete_task`, `yield_blocked`, `post_note`, `read_notes`, `read_contract`, `propose_contract_change`, `request_change` and `report_bug` (both become `task.added` for the owning role), `get_integration_status`.

**Retries.** A run that ends in an error, a conflicted merge or a reverted merge runs again once by itself (attempt + 1, with the reason in its prompt); after that the task waits for the user (retry, possibly with another model; skip; reassign to a role that owns its paths). A turn that ends without `complete_task` gets one nudge; `error_max_turns` gets one more run of turns in the same session; `yield_blocked` blocks the task with the agent's reason.

**Budgets.** Each session runs with a `maxBudgetUsd`: the planner a tenth of the squad budget (at least $1); a task its role's budget, else its share of the plan's estimate × 1.5 — always within what is left of its role, and within an equal share of what is left of the squad among the sessions that will run side by side. So parallel sessions can only overrun the squad by what each spends past its own cap (Claude Code checks after each response). After every turn the spend of the squad and of each role is compared with its limit: 75% warns once (`budget.warned`); 100% interrupts the sessions in scope (each gets 5 s to end its turn, then it is disposed), records `budget.exhausted` and pauses the squad. A task out of its own budget is blocked. Resuming may raise the squad's budget and some roles' (`squad.resume {budgetUsd, roleBudgets}` → `squad.budget_changed`), which re-arms the 75%/100% levels of the scopes that changed; without a raise, a squad that ran out can't resume.

**Pause, kill switch, restart.** Pause stops scheduling and interrupts the running sessions; their tasks go back to `ready` and, on resume, continue in the same Claude Code session (`resume`) and worktree. The tray's kill switch disposes squad sessions like any other; the orchestrator notices that it didn't dispose them itself and pauses the squad instead of retrying. On engine start, `recover()` puts tasks left `running` or `review` back to `ready` (a review whose merge had landed counts as done) and pauses every working squad ("Gravita restarted"), so nothing spends money until the user resumes; a squad that was planning plans again on resume. *Caveat:* a task that was interrupted and then outlived a restart has lost the id of its session; it starts a fresh session from its branch, and uncommitted work left in its worktree may be lost. Stop disposes every session and keeps the worktrees and branches.

**The brief as a conversation.** `squad.create` records `squad.created`, moves to phase `brief` and starts a *briefing* session of the planner role (`roleId: "planner"`, controllable, the brief as its first message, `origin: "gravita"`). It is read-only like the planner (tools `Read`/`Grep`/`Glob` plus `AskUserQuestion`, writes and `Bash` disallowed, cwd the repository's top level or the empty folder, model `models.planner`, no structured output) with a briefing charter: understand the goal, look around, ask a few short questions (choices preferred), state assumptions, never plan or write code, say when it knows enough. It runs in `default` mode, not `dontAsk`: `dontAsk` denies whatever isn't pre-approved without calling the permission callback, which would deny `AskUserQuestion` before it reaches the user; instead the policy allows reading, sends `AskUserQuestion` to Needs you and denies everything else. The user talks to it with `session.send`. Its budget is its own slice (a twentieth of the squad's, at least $0.50), counted in the squad's spend like every squad session. `squad.plan` (phase `brief` only, else 4011) moves to `planning` at once, interrupts a turn in flight (from Gravita's events: the main agent is active or waiting on the user; 5 s grace) and closes the session, then the planner **resumes that session** (`resume` + structured output + the planner charter, with "now produce the SquadPlan from everything above" as its message, its `maxBudgetUsd` its slice plus what the session already spent) and the usual validate/retry loop leads to `plan.proposed` and `review`. `squad.replan` resumes the planner role's session the same way. The session to resume is kept in memory only; when there is none (after a restart) or Claude Code can't resume it (the resumed session ends before its first turn), a fresh planner session gets the brief and the briefing as text — Claude Code's transcript when the engine can read it, else the message previews Gravita recorded (240 characters each), newest 12 000 characters. After a restart a squad in `brief` is left as it is (it isn't a working phase, so nothing pauses): its session isn't running, `session.send` to it is refused as not controllable, and `squad.plan` takes the fresh path. A briefing doesn't count as a working squad, but `squad.create` and `squad.plan` still check the limit of two.

**Limits on concurrency.** Squad sessions don't count against the six chats; a squad runs at most three role sessions, and at most two squads work at once.

## Addendum: the model policy

**Decision.** New squads default to an *Automatic* (cost-benefit) model policy instead of Opus everywhere. Opus costs about twice Sonnet per token and most squad work is routine; the expensive mistakes cluster in a few places. So the policy spends where a mistake ripples through the whole squad and saves everywhere else:

| Run | Automatic | Why |
| --- | --- | --- |
| Briefing conversation | Sonnet | Reading and asking; no decisions that are hard to undo. |
| Planning run (resumes the briefing) | Opus | One run, highest leverage: every role, path and contract comes from it. |
| Task, small or medium | Sonnet | Routine work inside one role's paths, checked by the commit gate and the checks. |
| Task: foundation, writes a contract path (`writes` overlapping a `contracts[].path`), or size `l` | Opus | Everything else builds on it, every role reads it, or it is big enough that a redo costs more than the model. |
| A later run of a task that struggled | one tier up per struggle (haiku → sonnet → opus, opus stays) | A second try on the same model tends to repeat the first. |
| Subagents of every squad session | Haiku | They search and read for their parent. |

The user can pick *Opus everywhere* or *Sonnet everywhere* instead (fixed: no lift, no escalation, subagents left alone). A role's own `model` in the plan wins over the policy for that role, and a manual "Retry with a stronger model" wins for that task.

**Shape.** `SquadModels` stays `{ planner, roles }` and gains optional `briefing` and `mode: "auto" | "fixed"`. Automatic is `{ mode: "auto", briefing: "sonnet", planner: "opus", roles: "sonnet" }`; `roles` is the everyday tier and the lift is relative to it. `squad.create` without `models` gets Automatic; with `models` and no `mode` it is fixed (an older client meant exactly those two models). Events from before the policy have no `mode` and project and run as fixed, the briefing on `planner` as before. One pure function in `@gravita/core`, `pickModel({ models, phase, plan?, task?, roleId?, escalations? })`, decides every model; the engine (briefing, planner, scheduler) and the UI (`estimatePlanCost`, the Board's Opus marks and per-model split, the "Retry with Opus" offer) both call it, so the estimate is the policy. `estimatePlanCost` takes optional per-task model overrides, and a task's budget slice prices that task at the model its run actually uses.

**Escalation is a fact in the log.** When an attempt ends in a way a stronger model may fix — a failure (including `complete_task` sent back past the limit for ownership or red task checks), an error, a conflicted merge, a merge undone by a red `integration` check, ending twice without `complete_task`, or running out of turns — the `task.status_changed` that closes it carries `struggledAttempt`. The projection keeps the distinct struggled attempts per task (`SquadTaskState.struggled`), order-tolerant and idempotent, and the escalation count is their number. The scheduler picks the model once per run from the projection (plus an in-memory manual override), so a restart picks the same model. Interruptions, the kill switch, `yield_blocked` and a spent budget are not the model's doing and don't escalate. Red *final* checks create new bug tasks; those start at their own tier.

**Switching model on resume.** The planner resumes the briefing's session on a different model. The runtime passes `model` to `query` whether or not it resumes, and Claude Code continues the transcript on the new model (the prompt cache doesn't carry over, which the estimate's cache-write share already assumes). The switch is recorded as a `session.settings` event on that session.

**Subagents.** The knob is the `CLAUDE_CODE_SUBAGENT_MODEL` environment variable, which the bundled Claude Code (2.1.296, SDK 0.3.296) lists among its known variables and reads when resolving a subagent's model: the model passed on the Agent call wins, then the agent definition's own `model` (Explore's built-in definition already picks Haiku), then this variable, then the parent's model. Under Automatic every squad session gets `CLAUDE_CODE_SUBAGENT_MODEL=haiku`; fixed choices don't set it. Gravita doesn't redefine built-in agents through the SDK's `agents` option, which would replace their definitions, and doesn't set `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, which would also override an explicit model an agent asked for.
